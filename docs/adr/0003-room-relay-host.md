# ADR-0003 房间、中继与房主交接

状态：已采纳（Owner 2026-11-25 选定快照方案 A）· 2026-11-25

## 背景

AGENTS.md 已定：房主浏览器是这一桌的服务器；服务端是哑管道（账号、大厅、建房、转发）；消息先走服务端转发，不上 WebRTC；回合制房主掉线换人接着当房主，实时游戏直接结束。

这里要定的是具体怎么分工，以及交接用的状态放在哪。

## 决定

1. **服务端知道"房间里有谁、谁是房主"，不知道"谁坐几号位、在玩什么"。** 成员和房主身份是网络层面的事实（谁连着、消息发给谁），只有服务端知道得准；座位、规则、游戏状态是平台层的事实，归房主。
2. **大厅信息是房主写的不透明 `meta`。** 服务端原样存、原样发给大厅订阅者，平台层的大厅界面自己解释里面的游戏名、人数。服务端代码里不出现任何游戏 id。
3. **转发只看 `to`。** `"host"`、`"all"` 或若干 userId。包体服务端不解析。
4. **房主选举由服务端做**：房主掉线 15 秒未重连，按入房顺序选下一个在线成员。规则简单、只依赖服务端已有的事实。
5. **快照由服务端暂存**：房主每次状态变化发一份，服务端只存最新一份、不解析，换房主时交给新房主（方案 A，下面保留当时的对比）。
6. **服务端只做防程序错误的兜底**：消息 ≤ 64 KB、单连接发送频率上限、只有房主能写 `meta` 和快照。不做防作弊。
7. **房间只在内存里。** 服务端重启房间就没了；部署时等房间清空再重启（ADR-0005），只改前端时不重启。

## 当时的对比：交接用的快照放在哪（已选 A）

AGENTS.md 原文是"回合制游戏把状态每回合同步给所有人，换个人接着当房主"。

**A. 房主每次状态变化把快照发给服务端，服务端只存最新一份（推荐）。** 换房主时服务端把这份快照交给新房主。
- 其他玩家的浏览器里始终只有自己那份视图，别人的手牌、狼人杀的身份不会出现在他们的内存和开发者工具里。朋友之间不防作弊，但"打开控制台不小心看到别人的牌"会让游戏变味，这样做顺手就避免了。
- 只有一份副本，没有"几个人手里的快照不一致，听谁的"的问题。
- 服务端多做的事：每个房间存一个几 KB 的不透明字符串。不解析，所以仍然是哑管道。
- 代价：服务端重启快照也没了——但服务端重启时房间本来就没了，不额外损失。

**B. 照原文，房主每回合把完整状态发给所有人，新房主用自己手里那份接着跑。**
- 服务端完全不存东西。
- 每个玩家的浏览器里都有完整状态（含所有人的手牌）。
- 掉线的瞬间各人手里的快照可能差一两步，新房主要先和大家对齐。

两种方案平台层的代码量差不多，差别是隐藏信息放不放到每个人的浏览器里。选 A 的话，AGENTS.md 那句改成"房主把状态每回合同步给服务端暂存"。

## 交接的细节（两种方案都适用）

- 快照带 `gameId`、`gameVersion`、`buildId`。新房主的游戏版本不一致就提示刷新，不硬接。
- 新房主恢复后给所有人重发视图；交接瞬间丢掉的操作，玩家看到"还轮到我"再点一次即可，不做重放队列。
- bot 跟着房主走：新房主的浏览器里重新创建 bot，bot 只依赖视图，所以没有 bot 状态要迁移。

## 不选的

- **服务端权威（像 boardgame.io 的 Master）**：服务端就得理解游戏，加游戏要改服务端、重新部署，违背已定原则。
- **WebRTC 点对点**：AGENTS.md 已说明，国内家宽打洞失败率高，最终还要 TURN。

## 什么时候重新考虑

- 实时游戏经服务端转发的延迟或 miao 的带宽不够用（先测：6 人坦克大约每秒几十到一百多 KB）。
