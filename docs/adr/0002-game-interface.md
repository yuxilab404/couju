# ADR-0002 游戏模块接口与确定性规则

状态：已采纳 · 2026-11-25

## 背景

AGENTS.md 要求：加新游戏只新增游戏代码 + 注册一次；接口一开始就要装下五个游戏的差异——回合制和实时、隐藏信息、2–12 人、固定队伍、阶段流程、本地 bot 和大模型 bot。规则要确定性，因为渲染、bot、测试、房主交接都靠同一份规则。

接口本身写在 [`ARCHITECTURE.md` §3](../../ARCHITECTURE.md#3-游戏接口)，本文记录为什么是这个形状，以及纸面推演。

## 决定

1. **一个游戏 = 一个 `GameDef` 对象**：`setup / turn 或 realtime / view / result / bot / ui`，外加 `players`、`teams?`、`options?` 声明。
2. **回合制和实时是两种规则形状，二选一**。回合制是"谁能动 + 校验 + 应用动作"；实时是"固定步长 + 每座位输入"。平台对两者走两条不同的循环，但房间、座位、bot 补位、结算是同一套。
3. **平台不认识阶段**。只问 `active(s)`（现在哪些座位能动，可以是多个）和 `timer(s)`（要不要倒计时）。阶段、轮次、叫牌、进贡都是游戏状态里的字段。
4. **隐藏信息靠 `view(s, seat)` 投影**。只有房主有完整状态，其他人只收到自己那份视图。
5. **随机数由平台持有、以参数传入**。`Rng` 的内部状态是几个整数，进快照；游戏不得用 `Math.random`、`Date.now`。
6. **时间以动作进入规则**。倒计时到点 → `onTimeout(s, seat)` 或 bot 产出一个普通动作。规则里没有时钟。
7. **bot 是每个游戏的必需品**，只吃 `view`，可以是同步、异步或带 `llm` 的异步。托管、补位、超时代打都是同一个 bot。
8. **一局的边界由游戏定**。斗地主一局 = 一手牌；掼蛋一局 = 从打 2 到过 A 的整场比赛（升级是状态的一部分）。平台只在 `result()` 非 null 时结算，`scores` 累计到房间记分板。
9. **画面是 React 组件**，props 是 `{ view, seat, act, seats, timer, ... }`；实时游戏额外拿到帧缓冲，在 `<canvas>` 里自己画。

## 为什么不更简单 / 更复杂

- 不做"平台通用阶段机"（像 boardgame.io 的 `phases/turn.order`）：五个游戏的流程差异很大（掼蛋的进贡还贡、狼人杀的夜里多角色同时行动），通用阶段机要么装不下，要么变成第二套规则语言。`active()` 一个函数就够平台调度。
- 不做"增量视图 / diff"：牌类视图几 KB，整份发最简单。实时游戏的帧本来就是整份。
- 不让游戏自己声明网络消息：游戏不碰网络，平台只认 `act`（回合制）和 `input`（实时）两种上行。

## 纸面推演

### 斗地主（第一个实现）

| 方面 | 落在哪 |
|---|---|
| 3 人，无固定队伍 | `players: {min:3,max:3}`；地主和农民是对局中决定的，属于状态，不用 `teams` |
| 叫分 → 出牌 → 结算 | 叫 1/2/3 分（Owner 已定）；状态字段 `phase`；`active()` 叫牌时是当前叫牌人，出牌时是当前出牌人 |
| 底牌、别人手牌 | `view` 只给自己的手牌、别人剩余张数、公开的底牌（叫完后）和出牌记录 |
| 倍数、春天 | 状态里累计，`result().scores` 给出三人得分 |
| 超时 | `timer()` 给当前玩家 30 秒；`onTimeout` 不提供 → bot 代打 |
| bot | 规则 bot，同步 |

### 掼蛋（固定队伍）

| 方面 | 落在哪 | 结论 |
|---|---|---|
| 4 人、对家一队 | `teams: () => [0,1,0,1]`；平台在入座时按队伍上色，换座位就是换队友 | ✓ |
| 两副牌 108 张、级牌、逢人配 | 规则内部；`setup` 用 `rng` 洗牌 | ✓ |
| 打 2 到过 A，多副牌连续 | 整场比赛是一局，`level`、`teamLevels` 在状态里；每副结束不算 `result`，过 A 才算 | ✓ |
| 进贡、还贡、抗贡 | 一个阶段，`active()` 返回需要进贡/还贡的座位（可能两人同时）；动作是"选一张牌"，`validate` 检查"必须进最大的""还贡 ≤10" | ✓ |
| 接风（出完的人由对家接着出） | 规则内部决定下一个 `active` | ✓ |
| 看不到对家的牌 | `view(s, seat)` 只含自己的手牌；对家的也不给 | ✓ |
| bot 配合对家 | bot 只看视图，视图里有完整出牌记录和各家剩余张数，足够做"让牌给对家"的判断 | ✓ |
| 一场 30–60 分钟，中途房主掉线 | 回合制，每次状态变化都发快照，换房主后接着打 | ✓ |
| 有人中途彻底离开 | 座位交给 bot 托管，游戏不知道座位后面是人还是 bot | ✓ |
| 想在房间里指定"谁和谁一队" | 入座阶段由平台按 `teams` 显示；房主可以拖人换座 | ✓ |

推演中发现的缺口：一开始的草稿里 `result` 是"每手牌结算一次"，装不下掼蛋的整场比赛。改成"一局的边界由游戏定"（决定 8）后解决。

### 迷宫坦克（实时，2–6 人）

| 方面 | 落在哪 | 结论 |
|---|---|---|
| 实时 | `realtime: { tickHz: 60, step(s, inputs, ctx) }`；输入是 `{up,down,left,right,fire}` 的按键状态 | ✓ |
| 迷宫随机生成 | `setup` 和每回合重开时用 `rng`；可以参考 ethanbaker/tank-trouble 的生成算法（Apache 2.0，搬代码要带协议） | ✓ |
| 没有隐藏信息 | `view(s, seat)` 对所有座位一样；平台发现游戏声明 `publicView: true` 就只广播一份，省带宽 | ✓（加了 `publicView` 声明） |
| 子弹反弹、碰撞 | `step` 里的纯计算；用整数或定点数避免浮点在不同浏览器上的差异（只有房主算，其实不要求跨机一致，但回放和测试需要） | ✓ |
| 网络延迟 | 非房主玩家按键 → 服务端 → 房主 → 服务端 → 自己，大约 100–200 ms。朋友间休闲对战可以接受；以后要更跟手，加一个可选的 `predict(view, input)` 让客户端先画自己的坦克，属于接口扩展，到时另写 ADR | ✓（已知局限） |
| 画面 | React 组件里一个 `<canvas>`，`requestAnimationFrame` 从帧缓冲取相邻两帧插值 | ✓ |
| 多回合积分，先到 N 分赢 | 状态里，最后 `result` | ✓ |
| bot | 每个 tick 拿视图出按键，本地脚本 | ✓ |
| 房主掉线 | 实时游戏不交接，回到等人 | ✓ |

推演中发现的缺口：广播同一份视图给所有人的优化需要游戏声明"视图公开"，加了 `publicView?: boolean`（默认 false）。

### 狼人杀（快速核对，以后做）

- 8–12 人；夜里狼人、预言家、女巫可以同时行动 → `active()` 返回多个座位 ✓。
- 白天按顺序发言、同时投票 → `active()` 依次一个人 / 一次所有存活者 ✓。发言是一个带文字的动作。
- 每段有时限 → `timer()` + `onTimeout`（发言超时就是"过"，不让 bot 代说）✓。
- 狼人互相认识、其他人看不到身份 → `view` ✓。
- bot 要说话 → `BotCtx.llm`，走服务端代理；大模型几秒到十几秒才回，期间局面可能变，平台回来后重新 `validate` ✓。

### 回旋镖乱斗（实时，2–4 人）

和坦克同一类，不重复推演。

## 代价

- 游戏作者要自己写 `view` 投影，写漏了会泄露信息。`conformance` 测试会用游戏提供的探针检查（例如斗地主：任何座位的视图里不得出现别的座位手牌的牌 id）。
- `apply` 必须返回新状态、不改旧状态。不引 immer，靠测试环境深冻结来抓错误。

## 什么时候重新考虑

- 出现一个游戏需要"平台不能统一提供"的能力（比如客户端预测、观战延迟）：补接口、写新 ADR，不在平台里为它开特例。
